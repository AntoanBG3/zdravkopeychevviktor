# ADR-002: База данни – SQLite + EF Core с миграции

Статус: Прието · 22.10.2026 · автор: Пейчев · преглед: целият екип

## Контекст
Учителят и клиентът трябва да стартират проекта след `git clone` и `dotnet run`, без да инсталират сървър за база данни (NFR-02). Схемата има пет свързани таблици (потребители, роли, екипи, проекти, заявки за отпуск) и ще се променя между спринтовете (T-02, NFR-05). Част от екипа работи на macOS, където SQL Server LocalDB не върви (NFR-07). Обемът е малък: десетки служители и стотици заявки.

## Решение
SQLite като файл `vacationmanager.db` до проекта, достъп през Entity Framework Core (`Microsoft.EntityFrameworkCore.Sqlite`). Схемата се описва в `ApplicationDbContext` и се променя само с миграции в папка `Migrations/`. При стартиране `DbSeeder.SeedAsync` извиква `Database.MigrateAsync()` и, ако базата е празна, създава ролите и тестовите потребители `admin`, `lead`, `dev` (T-03).

## Последици
(+) нулева инсталация: базата се създава сама при първото `dotnet run`
(+) еднакво поведение на Windows и macOS; базата е един файл, който се копира или изтрива
(+) миграциите пазят историята на схемата в Git
(−) един писател в даден момент; при много едновременни одобрения ще има изчакване (при нашия обем не е проблем)
(−) за реален продукт с много потребители ще трябва смяна на доставчика (PostgreSQL или SQL Server) и нови миграции
(−) EF Core е версия 9 върху .NET 10; работи, но при следваща промяна на схемата е добре да минем на EF Core 10
(−) `vacationmanager.db` в момента е качен в Git заедно с `bin/` и `obj/`; трябва `.gitignore`, иначе всеки локален тест на някого създава конфликти

## Алтернативи
SQL Server Express / LocalDB – отделен сървър, LocalDB е само за Windows. PostgreSQL – отделен сървър, допълнителна настройка на потребител и база. Сравнението е в [раздел 3](../01-избор-на-технологии.md#3-сравнение-на-базите-данни).
